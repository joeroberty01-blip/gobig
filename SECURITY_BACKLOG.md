Last full review: **2026-09-26** (Phase 13 security & performance audit). Previous: 2026-09-24 (Phase 4). Feature reviews done for Phase 4 (location), Phase 5 (trust & verification) and Phase 6 (connection system). Reviewer: Claude (Opus 5.5).

## Current posture (summary)

| Area | Status |
|---|---|
| Authentication | TOTP two-factor required for ADMIN/SUPER_ADMIN (encrypted secret, replay-protected, hashed recovery codes; admin powers withheld until the session passed it); common passwords refused; reset token only in the URL fragment; bcrypt hashes; single-use, hashed, 30-min reset tokens; sessions checked against DB on every gated request (role/status/password-change); same message for unknown account vs wrong password; constant-time-ish login (dummy hash); rate limits on login (per identifier + IP), sign-up, reset (SEC-010). |
| Authorization | Three layers: `proxy.ts` route gate → `can()` in every server action/route → ownership from session (providerId is never taken from the client). Admin creation limited to SUPER_ADMIN; roles can't be self-assigned. |
| IDOR | Provider writes scoped by session-derived `providerId`; media delete scoped by provider (integration-tested); public profile hidden unless ACTIVE or owner/admin. Service requests (Phase 7): customers read only their own (`customerId` from session), providers only requests they were matched to (`requestId_providerId`), messages only by the two parties of that conversation (side derived server-side), request photos only via an access-checked route; everything else is a 404. Integration-tested. |
| Mass assignment | Every write goes through an explicit Zod schema + explicit Prisma `data` fields. Regression-tested. |
| Database | FKs, uniques, CHECK constraints (prices, coords, hours, one owner, one logo/cover), partial unique indexes, transactions for multi-step writes; separate Neon test branch with guards. |
| API | Parameterised SQL only (`Prisma.sql`), regex input escaped, query length capped (100 chars, 6 words), candidate cap (500), pagination. |
| Privacy | Provider exact coordinates / address only public when provider chose EXACT; approximate = fixed ~550 m grid; area-only = area centre; distances no more precise than the public point; radius coverage from the public point (SEC-020); contact numbers only for enabled buttons; photo EXIF (GPS) stripped; customer position only on request, rounded ~110 m, httpOnly cookie for 1 day, never stored server-side. |
| Files | Server re-encodes every image (sharp) → WebP, format allow-list, 5 MB cap, pixel cap, unguessable keys, owner-scoped delete, same-origin check. |
| Secrets | None in source (scanned). `.env*` git-ignored. See SEC-004 about rotation. |
| Headers | nosniff, Referrer-Policy, X-Frame-Options DENY, frame-ancestors, Permissions-Policy, HSTS (prod), no `X-Powered-By`. Nonce-based CSP on every page (SEC-007). |
| Verification & reviews | Providers can request but never decide verification; decisions admin-only, race-safe, audited; documents in a private bucket via 60 s signed URLs with logged views; one review per customer per provider, no self/competitor reviews, replies can't alter reviews, moderation audited; append-only audit log (DB triggers). |
| Provider analytics (Phase 10) | Views/appearances stored as salted daily hashes only (no IP, account or search text); owner/staff/admin, bots and prefetches excluded; recorded after the response; providers see aggregates of their own business only (`analytics:view-own`, provider id from the session); favourites show counts, never names. |
| Contact buttons & analytics | Booking links validated (http/https only); contact details sent only for enabled buttons; tap beacon same-origin, rate-limited, always 204; one row per person/button/day; only salted daily visitor hashes stored (no IP/account); own-staff and admin taps ignored. |
| Ranking | Organic signals only, all measured from provider data; strict weights schema (no paid/unknown keys; relevance can't be 0); admin-only, audited changes; stored weights re-sanitised on read; distance from the public point only. |
| Requests & messaging | Customer address, phone and email hidden from providers until that provider is accepted; customer shown as "First L."; request photos in the private bucket (EXIF stripped, 5-min signed URLs, 404 to anyone else); notifications store ids only (no message text or numbers); race-safe acceptance (conditional update + one-accepted-quote unique index); CHECK constraints on budgets, time, amounts, message length; rate limits on requests, photos, quotes, messages; open requests capped at 5 per customer. |
| Admin platform (Phase 12) | Every admin page gated by proxy + `can()` + page check; ADMIN vs SUPER_ADMIN split (policy, other admins, announcements, settings); no self-changes; reasons required and audited for suspensions, request closures, report outcomes; nothing destructive (switch-off, not delete); conversations visible to admins only via a report, with each view logged. |
| AI | Model output restricted by a schema built from the catalogue and re-validated server-side; no model-written text shown to users; customer text sent only as the user turn and treated as data; no provider data sent to the model; key server-only; queries not stored or logged; rate-limited with a free rule-based fallback. |
| Payments & paid placement (Phase 11) | No card data handled: admins record mobile-money/bank references; exact-amount check, unique reference, one open subscription per provider (DB index), CHECK constraints on prices/dates; all billing actions audited; prices/settings super-admin only; paid placement only in labelled Sponsored blocks, only for providers already in the organic results, organic order unchanged (tested); plans never affect badges, verification, ratings or ranking. |

Authentication · Authorization · Ownership · Input validation · Database access · Data privacy ·
API security · Data integrity · Error handling · Rate limiting.


### Phase 16 security review (2026-09-26)

Scale foundation: job queue, optional Redis, read replica, field encryption, health and tick endpoints,
request ids, structured logs. Checked: `/api/health` reveals only up/down per dependency and a short
commit id; `/api/cron/tick` is POST-only, 404 without the exact bearer secret; the queue writes a
result only while the worker still holds the job's lock; Redis failures fall back to Postgres
(fail-open to the *existing* limiter, never to "no limit"); the replica is used only for public
discovery reads. API route sweep (IDOR): every route takes the owner from the session
(`getOwnedProviderId`, `customerId` in the query) or checks `can()`; private objects are served by
short-lived signed URLs after an ownership check and 404 for everyone else. Found and fixed SEC-046.


### Phase 17 security review (2026-09-26)

Rides & deliveries. Checked: every server action takes the customer/provider id from the session and
the service re-checks ownership or assignment; `/api/trips/[id]` returns 404 to anyone but the trip's
customer or its (offered/assigned) driver; offered drivers see labels and distances only; exact data
decrypts only for the accepted driver during an active trip and for the customer; state changes are
guarded single-statement updates (race test: two drivers accept at once → exactly one wins);
sample businesses and unverified providers can't go online; fares and payment are records only (no
payment data); admin trips page reads labels only; notifications store ids, and their text is built
from area labels. Also stripped admin-only text (`trust.admin`, `billing.admin`, trips admin labels)
from the dictionary sent to every visitor.


### Settings centre & automation review (2026-09-28)

Checked: only `settings:manage` (super admin, after 2FA) can save; admins can view. Every numeric
setting is range-checked server-side (zod), so a compromised session can't set e.g. 0-day retention
or unbounded radii; saves are audited with before/after. Automation acts as the system (actorId
null), is idempotent (reminders are claimed with a guarded update before notifying; review hiding
uses a status guard), never deletes data, and is audit-logged. The status panel shows up/down and
counts only — no hostnames, keys or error text. Feature switches are enforced in the service layer
(`requestTrip`), not just hidden in the UI.


### Phase 19 load testing & hardening (2026-09-28)

Tools: `npm run load:serve` (production build on the TEST database and storage, port 3003),
`npm run load:http`, `npm run load:dispatch`. Findings fixed: SEC-052 (spoofable client address),
SEC-053 (double assignment under concurrency), SEC-054 (no shared caching), SEC-055 (health check vs
database cold start), plus per-driver notification lookups batched into one query and queue workers
limitable by job type. Measured from Tanzania (~200 ms per database round trip), so absolute
latencies are pessimistic; the production server sits next to the database.
